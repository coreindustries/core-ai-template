# Database Migrations — Structure & Discipline

Auto-loaded rule. Default platform: **Supabase (Postgres)**. Adapt for Prisma / Drizzle / Alembic / golang-migrate by mapping the commands; the invariants below are platform-agnostic.

## Core Directive

**Every schema change ships as a numbered, timestamped, committed migration file.** No `db push` to non-dev databases. No `ALTER TABLE` typed into a psql prompt. No "I'll backfill manually after deploy." The migration *is* the change.

Migrations are:

- **Forward-only by default.** Rollbacks are real code (down migrations or explicit reverse migrations), written during development, tested, but used only as a last resort — the preferred recovery is a roll-forward fix.
- **Idempotent-safe when possible** (`IF NOT EXISTS`, `IF EXISTS`, `ON CONFLICT DO NOTHING`) so re-running on a partially-migrated database converges.
- **Reviewed.** Schema changes are high-blast-radius and get a second set of eyes before merging.

## Rule 1 — Canonical structure (Supabase default)

```
supabase/
├── config.toml                          # Supabase CLI config
├── migrations/
│   ├── 20260421093000_create_users.sql
│   ├── 20260421094500_add_user_email_unique.sql
│   └── 20260421101500_add_posts_rls_policies.sql
├── seed.sql                             # Deterministic seed data (dev/staging only)
├── tests/
│   └── users_rls.test.sql               # pgTAP tests for RLS policies
└── functions/                           # Database functions (if any)
    └── hello/
        └── index.ts
```

**File naming**: `YYYYMMDDHHMMSS_<imperative_snake_case>.sql`. Timestamp is UTC. Generated by `supabase migration new <name>` — do not hand-format.

**One migration = one logical change.** Adding `users` + its RLS + its trigger can live in one file; adding `users` + an unrelated `invoices` table splits into two.

**Never edit a committed migration.** Once a migration is merged to `main`, it's immutable. To undo: write a new migration that reverses it. Editing a committed migration silently diverges schemas across environments.

## Rule 2 — Migration content conventions

### Always

- **Statement terminator**: every statement ends with `;`.
- **Explicit schema**: qualify objects — `public.users`, not `users`. Supabase has multiple schemas (`auth`, `storage`, `realtime`, `public`); implicit resolution is a footgun.
- **Explicit transaction boundary for multi-statement migrations**:
  ```sql
  begin;
  -- statements
  commit;
  ```
  Supabase CLI wraps each file in a transaction by default; declare it explicitly anyway for clarity and to catch errors that abort mid-file.
- **RLS on every table with tenant / user data**:
  ```sql
  alter table public.posts enable row level security;
  create policy "posts_select_own" on public.posts
    for select using (auth.uid() = author_id);
  ```
  A migration that creates a user-facing table without RLS is a P0 bug. CI gates this (see Rule 5).
- **`updated_at` triggers** for tables that have one:
  ```sql
  create trigger set_updated_at before update on public.posts
    for each row execute function public.set_updated_at();
  ```
- **Comments on non-obvious columns**: `comment on column public.users.status is 'active | archived | suspended';`.

### Never

- `drop table` on a non-empty production table without a multi-step plan (see Rule 4). Same for `drop column`, `alter column type`, `rename`.
- `delete from` / `update` without a `where` on production schemas. Data migrations go in a separately-reviewed file.
- `create index` (blocking) on large tables in production. Use `create index concurrently` — but note that `concurrently` cannot run inside a transaction, so that migration file must contain *only* the index statement and explicitly opt out of the transaction wrapper.
- Hand-edit `supabase/migrations/*` after commit.

## Rule 3 — Development flow

1. **Start a feature branch.**
2. **Make the schema change locally**:
   ```bash
   supabase migration new add_comments_table
   # edit supabase/migrations/<timestamp>_add_comments_table.sql
   supabase db reset   # applies all migrations to the local Supabase (fresh DB)
   ```
3. **Regenerate types** (if using generated types):
   ```bash
   supabase gen types typescript --local > src/types/supabase.ts
   ```
4. **Write or update tests** (see Rule 6).
5. **Commit the migration + generated types + code in the same PR.**
6. **CI**:
   - Spins up a fresh Supabase local stack
   - Applies migrations from scratch
   - Runs pgTAP tests + app test suite
   - Diffs the result against the checked-in types
7. **Merge → deploy**:
   ```bash
   # Via GitHub Actions, on protected branch
   supabase db push --db-url "$PROD_DB_URL"
   ```

Local db iteration pattern: `supabase migration new → edit → supabase db reset → test → repeat`. Never `supabase db push` to a remote environment directly from a dev machine.

## Rule 4 — High-risk schema changes (expand/contract)

Any of these is a multi-PR, multi-deploy sequence — never a single migration:

- Renaming a column in a high-write table
- Changing a column type (including `varchar → text`, `int → bigint`)
- Dropping a column still in use
- Adding a `not null` to an existing column
- Backfilling a new column from existing data on a large table

**Expand/contract pattern**:

1. **Expand migration**: add the new shape alongside the old. Both read and write go to both.
2. **Backfill** (in its own migration or a job): populate the new shape from the old.
3. **Migrate reads**: application code switches to reading the new shape. Old shape still populated.
4. **Migrate writes**: application switches to writing only the new shape.
5. **Contract migration**: drop the old shape (column, table, constraint).

Each step ships and soaks before the next. For tables > 10M rows, steps 2 and 5 may need batching and downtime windows documented in the PR.

## Rule 5 — Enforcement gates

| Gate | Where | Fails on |
|---|---|---|
| `supabase db lint` (built-in linter) | Pre-commit + CI | RLS missing, tables without primary keys, obvious SQL issues |
| `scripts/assert-migration-conventions.sh` | Pre-commit + CI | Filename not matching `YYYYMMDDHHMMSS_*.sql`, editing an already-committed migration, new table without RLS |
| pgTAP test suite | CI | RLS policy gaps, function behavior |
| `supabase db diff` | CI (dry-run) | Schema drift between migrations and live |
| Migration review label | PR | Human signs off on any migration |

## Rule 6 — Testing migrations

- **pgTAP** in `supabase/tests/*.test.sql` for RLS policies and database functions. Run via `supabase test db` (or `pg_prove` for CI without Supabase CLI).
- **Integration tests** in the app suite use a fresh migrated database (`supabase db reset --local` in the CI setup step).
- **Never test against a snapshot of prod** — regenerate from migrations on every test run. This catches a migration that runs fine against today's data but breaks against an empty DB.
- **Each new RLS policy gets a pgTAP test** that asserts both positive (the right user sees the row) and negative (the wrong user does not) cases.

## Rule 7 — Environments & deployment

- **Local**: `supabase start` → fresh Supabase stack (Postgres, PostgREST, GoTrue, Realtime, Storage). `supabase db reset` applies migrations.
- **Preview** (PR builds): ephemeral Supabase project created via the [Preview Branches](https://supabase.com/docs/guides/platform/branching) feature. Migrations applied on PR open, destroyed on PR close.
- **Staging**: long-lived Supabase project; `supabase db push --db-url "$STAGING_DB_URL"` on merge to `main`.
- **Production**: same, with manual gate. Production deploys are always: (1) migration applied, (2) app deploy. Never the reverse, never simultaneous.

**Database URLs come from chamber**: `chamber exec <service> -- supabase db push` — never paste a connection string containing a password into a shell.

## Rule 8 — Agent behavior

An AI agent modifying the schema must:

- **Always** generate a new migration file via `supabase migration new <name>`. Never write directly to `supabase/migrations/` without the CLI.
- **Never** edit a migration file whose filename is older than the current HEAD (i.e. merged already).
- **Always** include RLS on any new user-data table in the same migration.
- **Always** regenerate types (`supabase gen types`) in the same PR.
- **When asked** to make a breaking change (drop/rename column on existing table): respond with the expand/contract plan from Rule 4. Do not execute step 5 of expand/contract in the same PR as step 1.
- **Refuse** to run `supabase db push` against any URL containing "prod" without explicit user confirmation in-session.
- **Refuse** to edit `supabase/migrations/*.sql` that's already committed; write a new migration instead.

If an agent discovers a drift between migrations and live schema (manual change applied out-of-band), stop and surface it: `supabase db diff --linked` shows the delta. Do not auto-generate a "fix" migration without user review.

## Switching off Supabase

If a project uses a different stack (raw Postgres + golang-migrate, MySQL + Alembic, etc.), the invariants above still apply:

- Numbered, timestamped, committed migration files
- Never edit committed migrations
- Expand/contract for breaking changes
- CI applies migrations from scratch against a fresh DB
- Lint + review gate on every migration

Override `prd/00_technology.md` → Data Layer with the project's choice and update `Makefile` db targets. The rule file's invariants don't change; only the commands do.
