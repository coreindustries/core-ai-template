# Supabase — Local & CI Setup

Schema, migrations, seed data, and RLS tests for this project's Postgres database.
See `.claude/rules/database-migrations.md` for the full directive and `docs/decisions/0003-supabase-migrations.md` for the decision rationale.

## Layout

```
supabase/
├── config.toml                          # Supabase CLI config (generated by `supabase init`)
├── migrations/                          # Numbered, timestamped SQL migrations
│   └── YYYYMMDDHHMMSS_<name>.sql
├── seed.sql                             # Deterministic seed data (dev/staging only)
├── tests/                               # pgTAP tests for RLS + functions
│   └── *_rls.test.sql
└── functions/                           # Database functions (if any)
```

## One-time setup

```bash
brew install supabase/tap/supabase       # macOS
# or: https://supabase.com/docs/guides/cli
supabase init                            # Creates supabase/config.toml
supabase login                           # Authenticates the CLI (stores token in keychain, not on disk)
supabase link --project-ref <ref>        # Associates this repo with a Supabase project
```

## Daily loop

```bash
# Start local Supabase stack (Postgres + GoTrue + PostgREST + Realtime + Storage)
supabase start

# Create a migration
supabase migration new add_posts_table

# Edit supabase/migrations/<timestamp>_add_posts_table.sql
# ... write SQL ...

# Apply all migrations to a fresh local DB (destructive — local only)
supabase db reset

# Regenerate types for the app
supabase gen types typescript --local > src/types/supabase.ts

# Run database tests (pgTAP)
supabase test db
```

## Deploying migrations

```bash
# Staging (via chamber — DB URL is a secret, never paste it)
chamber exec <service>-staging -- supabase db push --db-url "$DATABASE_URL"

# Production (usually via GitHub Actions, not local)
chamber exec <service>-prod -- supabase db push --db-url "$DATABASE_URL"
```

CI runs migrations on PR open against a preview branch and on merge to `main` against staging. Production deploys are gated on a manual approval.

## Writing a migration — quick checklist

- [ ] Generated via `supabase migration new <imperative_snake_case_name>`
- [ ] Statement terminator (`;`) on every statement
- [ ] Schema-qualified (`public.users`, not `users`)
- [ ] Wrapped in `begin; ... commit;` for multi-statement files
- [ ] New tables with user data have `alter table ... enable row level security;` and at least one policy
- [ ] `updated_at` trigger wired up if the table has that column
- [ ] No `drop`, `rename`, or type-change on non-empty production tables without an expand/contract plan (see rule file)
- [ ] `create index` on large tables uses `concurrently` (and lives alone in its own migration file with the transaction wrapper removed)
- [ ] Added a pgTAP test in `supabase/tests/` for every new RLS policy
- [ ] Ran `supabase db reset` locally and everything applies cleanly from scratch

## Common patterns

### Enabling RLS on a new table

```sql
create table public.posts (
  id uuid primary key default gen_random_uuid(),
  author_id uuid not null references auth.users(id) on delete cascade,
  title text not null check (length(title) between 1 and 200),
  body text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

alter table public.posts enable row level security;

create policy "posts_select_own" on public.posts
  for select using (auth.uid() = author_id);

create policy "posts_insert_own" on public.posts
  for insert with check (auth.uid() = author_id);

create policy "posts_update_own" on public.posts
  for update using (auth.uid() = author_id) with check (auth.uid() = author_id);

create policy "posts_delete_own" on public.posts
  for delete using (auth.uid() = author_id);

create trigger set_posts_updated_at before update on public.posts
  for each row execute function public.set_updated_at();

comment on table public.posts is 'User-authored posts; RLS-scoped to author.';
```

### pgTAP test for the above

```sql
-- supabase/tests/posts_rls.test.sql
begin;
select plan(4);

-- setup: two users, one post each
select tests.create_supabase_user('alice');
select tests.create_supabase_user('bob');
select tests.authenticate_as('alice');
insert into public.posts (author_id, title) values (tests.get_supabase_uid('alice'), 'Alice post');
select tests.authenticate_as('bob');
insert into public.posts (author_id, title) values (tests.get_supabase_uid('bob'), 'Bob post');

-- alice sees only her own
select tests.authenticate_as('alice');
select is((select count(*) from public.posts)::int, 1, 'alice sees 1 post');

-- bob cannot see alice's
select tests.authenticate_as('bob');
select is((select count(*) from public.posts where title = 'Alice post')::int, 0, 'bob cannot see alice post');

-- insert with wrong author_id is blocked
select tests.authenticate_as('bob');
select throws_ok(
  $$ insert into public.posts (author_id, title) values (tests.get_supabase_uid('alice'), 'forged') $$,
  '42501'
);

-- cross-user update is blocked
select tests.authenticate_as('bob');
select is((update public.posts set title = 'hacked' where title = 'Alice post' returning 1)::int, null, 'bob cannot update alice post');

select * from finish();
rollback;
```

### Expand/contract: renaming a column

**Migration 1 (expand)**: add new column, backfill trigger, dual-write in app code.
**Migration 2 (backfill)**: one-time `UPDATE` to copy old → new where null.
**Migration 3 (contract)**: drop old column (only after app no longer reads/writes it — usually a separate release).

See `.claude/rules/database-migrations.md` Rule 4.
